**How to read the evidence column.** _Code_ means read in the source. _Test_ means covered by an automated test. _Real-DB_ means a test run against the staging PostgreSQL database; these do not run in CI. _Live_ means observed on the deployed API. _Inferred_ means concluded from the code but not observed. ## 2. What happens when something fails

| Failure                                                                          | Effect                                                                                                                                                                               | Recovery                                                                                                                              |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| The reply to a booking is lost after the booking committed                       | The customer's page, which keeps its key across a lost reply, sends the same request again and gets the same booking (200).                                                          | The manage code was emailed on confirmation, so the customer has it. _Inferred for the page: the page code was not run in a browser._ |
| The reply is lost and the request had no key (an older cached page)              | A 409 for a booking that exists.                                                                                                                                                     | The customer uses the emailed link. _Inferred._                                                                                       |
| The database cannot be reached                                                   | The booking route answers 503. The payment webhook answers 503, so the provider sends it again.                                                                                      | Automatic, on the provider's retry                                                                                                    |
| The provider cannot be asked for a subscription's current state                  | Nothing changes and the event is not recorded. The webhook answers 503, so the provider sends it again. A subscription the provider does not know is not a failure: nothing changes. | Automatic, on the provider's retry                                                                                                    |
| A table or column the code needs is missing (code deployed before its migration) | A database error the webhook route does not map, so an unhandled server error and a provider retry.                                                                                  | Apply the migration, then the retry succeeds. _Inferred from the code; not observed._                                                 |
| A payment arrives after its time was taken                                       | Marked paid, not confirmed, error logged.                                                                                                                                            | Manual refund                                                                                                                         |
| A payment already belongs to another booking                                     | Ignored, error logged with the constraint name.                                                                                                                                      | Manual review                                                                                                                         |
| A refund call to the provider fails                                              | The booking is left as it was.                                                                                                                                                       | The customer or owner repeats the cancel; a refund already made is found                                                              |
| The email provider fails                                                         | The change stays; the failure is recorded in the email log.                                                                                                                          | Resend manually                                                                                                                       |
| A signed notification is wrong or unsigned                                       | 400, nothing is applied.                                                                                                                                                             | None needed                                                                                                                           |
| A provider that is not live sends a notification                                 | 501                                                                                                                                                                                  | None needed                                                                                                                           |

## 3. Operating rules these changes depend on

1. **Apply a migration before the code that uses it runs.** The event record (0017) and the idempotency key (0018) are written by the code on every relevant event or booking. A migration that is additive and unused by the older code is safe to apply first. One change (0017) was merged before its migration was applied; the window's effect was not observed.
2. **A migration is one atomic statement.** From 0016 on, the change and its ledger row are in one `DO` block. A test enforces that each file records itself.
3. **Real-database tests are the evidence for these paths, and they do not run in CI.** CI runs the unit tests and checks only. A reviewer who relies on CI alone has not seen these tests run.

## 4. Not verified, and open

- **A live Stripe test event writing the event record.** Observed on staging on 23 November 2026: one test payment wrote one record. A repeat delivery of a live event was not tried, so ignoring a repeat is still covered only by tests.
- **The booking page in a browser.** A paid booking was made in a desktop browser on staging on 23 November 2026, and it carried an idempotency key. The key's lifetime in the page (kept across a lost reply, dropped after a definite answer) is untested.
- **The paid path end to end.** Run once on staging on 23 November 2026, in Stripe test mode: the hold, the checkout, the payment notification and the confirmation, then a move and a customer cancel with a full refund, with the confirmation, move and cancel emails to the customer and the owner. The refund was not checked in the provider's dashboard. A declined card and an expired hold were not run.
- **Retention.** Event records and idempotency keys have no expiry. Rows grow with use. No retention period is decided.
- **Ordering of booking payment events.** Out-of-order delivery of booking payment events is not addressed. The event record recognises repeats, not order. Subscription notifications are not affected by order, because the subscription's current state is read from the provider.
- **Subscription notifications against Stripe.** The read of the current state was tested with a fake Stripe client only. It has not been run against Stripe's test mode.
- **Migrations 0001 to 0014** are not atomic, and there is no migration runner. Applying every file, 0001 to 0019, to an empty database was rehearsed on 17 November 2026 (see `RESTORE.md`).
- **The concurrency tests are timing-dependent.** They show the behaviour held in the runs made.
